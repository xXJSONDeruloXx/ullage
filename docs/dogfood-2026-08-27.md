## METAL GEAR SOLID 4 boot investigation — AppID 2492670

The user downloaded the Windows depot for `METAL GEAR SOLID 4: Guns of the
Patriots - Master Collection Version`. Steam finished the staged update and
verification before the first test; the installed manifest reported build
`24921893`, depot `2492671`, and `24,501,734,674` bytes on disk. Ullage used
the fresh runtime package above, `gamehub-container-5`, the existing native
Steam client, and the default mapped entry `Launcher/launcher.exe`.

The investigation was run in progressively more specific layers:

1. Native Steam Play reached the mapped launcher and entered `App Running`.
   The launcher stayed alive without creating `mgs4.exe` or a usable game
   surface. A fresh capture showed the launcher-owned `Steam Error` dialog:
   `Application load error 3:0000065432`.
2. A direct diagnostic launch of the shipped launcher reproduced the same
   error. Wine relay tracing showed the launcher attempting to open
   `Local\\SteamStart_SharedMemLock` and
   `Local\\SteamStart_SharedMemFile`; both opens returned null before the
   launcher displayed the dialog. The trace also showed the launcher later
   calling `TerminateProcess(-1, 0x33)` on its failure path.
3. A separately staged, unmodified copy of the game's `steam_api64.dll`
   passed `SteamAPI_Init`, pipe/user creation, logged-on identity, matching
   AppID `2492670`, subscription, DLC enumeration, and shutdown through the
   same Ullage runtime. This rules out a basic lsteamclient load, identity, or
   ownership failure, but it is a diagnostic process rather than a claim that
   the shipped game reached its own API calls.
4. A read-only `tools/ullage-steamstart-probe.c` was compiled with MinGW and
   run while GameHub's SteamAgent launch was active. It returned
   `ERROR_FILE_NOT_FOUND` for both named objects. The GameHub log confirmed
   that its SteamAgent launched `launcher.exe`, then only tracked the
   launcher and crash handler; no `mgs4.exe` was created.
5. The local stock Valve Steam client DLL set was copied into a disposable
   prefix with the open-source reference launcher. `steamclient64.dll`,
   `tier0_s64.dll`, `vstdlib_s64.dll`, and the crash handler loaded, proving
   that the remaining gap is not simply a missing companion DLL. That prefix
   had no authenticated Steam session, and its Steam service could not start;
   the direct launcher still exited without a game surface.

Static inspection of the stock Valve `steamclient64.dll` showed that the
Windows-side Steam DRM service owns the 1 KiB shared mapping, initializes the
version/state fields, and consumes the launcher-written AppID/status fields.
The small relay experiment could acknowledge the launcher's event wait, but
that was not enough: the launcher then followed its DRM failure path. A
GameHub `SteamAgent.vmp.exe` launch is therefore not equivalent to a full
Windows Steam client/DRM service for this title.

The current result is deliberately recorded as a boundary, not a forced
“fix”: Ullage launch mapping, SteamAPI initialization/ownership, supervision,
and cleanup passed; MGS4 renderer/boot acceptance failed before `mgs4.exe`.
The native Stop path and direct diagnostic stop both left a clean prefix with
no residual Wine or game processes. No shipped executable was patched or
replaced. No Steamless swap, third-party DRM binary, or `OnlineFix`
`StubDRM64.dll` was used; the installed depot and account-bearing Steam state
remain the source of truth.

The durable diagnostic source is
[`tools/ullage-steamstart-probe.c`](../tools/ullage-steamstart-probe.c). The
next legitimate boot gate is a compatible Windows-side Steam DRM startup
service or a documented, redistributable title-compatible implementation;
adding a named-object acknowledgement alone is insufficient. This title is
not counted as a renderer pass until `mgs4.exe` reaches a visible surface.

1. GameNative's newest bionic-Steam path launches a dedicated host process,

   graphics solve the next runtime boundary. None of those layers supplies
   the Windows-side SteamStart/DRM backend that MGS4 rejected in the native

No refreshed Android research file contains an MGS4-specific result, so no
Android success is being counted as evidence for this title. Apple Silicon
already has an x86_64 execution path through the current Wine/GPTK runtime;
the observed failure is earlier than rendering. The next high-value Ullage
work is therefore to model the authenticated Steam bootstrap/session boundary
and title-compatible SteamStart service, while preserving the shipped game
files and `steam_api64.dll` contract.

Compatibility experiments remain allowed only when they preserve the user's
Steam installation and are reversible—for example, changing a documented
runtime, prefix, or legitimate Steam-client component. Executable patching,
Steamless/OnlineFix-style license bypasses, and substituting a fake
`StubDRM64.dll` are explicitly not part of the legitimate pass. If a future
isolated experiment only demonstrates that the renderer works after DRM is
removed, it must be labeled as a lower-tier diagnostic and cannot advance the
MGS4 acceptance row.

## Steamworks probe correction and exact forwarder validation — 2026-08-27

The first MGS4 Steamworks probe in this investigation had a harness defect: it
passed the AppID twice to the flat
`SteamAPI_ISteamApps_BGetDLCDataByIndex` entry point. The documented ABI takes
the interface pointer, DLC index, output AppID, availability flag, name
buffer, and buffer length. The probe now uses that signature. The earlier
`0xBEEF` access violation was therefore a diagnostic-harness error, not
evidence of a product bridge fault.

With the corrected probe and Ullage's exact x64 `steamclient64.dll` forwarder
staged into the disposable prefix, both game DLL copies passed independently:

* `MGS4/steam_api64.dll`.
* `Launcher/launcher_Data/Plugins/x86_64/steam_api64.dll`.

Each run completed `SteamAPI_Init`, Steam identity, AppID matching,
subscription and ownership checks, all three MGS4 DLC records, stats and
achievement enumeration, and `SteamAPI_Shutdown` with exit status 0. The
reported Steam identity matched the installed account and the AppID was
`2492670`. The reported `steam_logged_on=0` matters: this proves the public Steamworks DLL
transport and ownership metadata path, not an authenticated Windows Steam
client session or a completed DRM ticket exchange.

The real forwarder launch remains a separate failure. The unmodified
`Launcher/launcher.exe` loads `UnityPlayer.dll` and the Steam API, and its
Wine window receives focus, but it never loads `GameAssembly.dll` or starts
`mgs4.exe`; it eventually exits or waits in the Cocoa event loop without a
usable game surface. Direct `MGS4/mgs4.exe` loads its native dependencies and
the same public Steam interfaces, then exits without leaving a game process or
visible surface. The older GameHub/native path observed unavailable
`SteamStart_SharedMemLock` and `SteamStart_SharedMemFile` objects; the direct
forwarder trace did not reach those calls, so this run does not claim that the
named-object handshake occurred.

After each test the temporary prefix was restored to its stock Valve client
(`steamclient64.dll` SHA-256
`86112382982fa855086f566b2fb8343290e798849029337dcfeecba0d5051b5e`). No
installed game files, native Steam files, credentials, or executable DRM state
were changed. No Steamless/OnlineFix-style removal, fake DRM DLL, or license
bypass was used. This closes the public Steamworks bridge gate while leaving
the legitimate launcher/private Steam client-session boundary open.
